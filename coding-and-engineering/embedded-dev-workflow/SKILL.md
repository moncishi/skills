# 嵌入式 AI 辅助开发工作流（Embedded Dev Workflow）

## 核心原则：把板子事实放进上下文，主动打断假设锚定

大模型每一步生成都依赖当前上下文里的事实。缺少项目与板级事实时，模型会退回到训练数据里的“最常见情况”（例如默认猜 SGMII 1G、写出通用 Linux/U-Boot 命令、或直接修改 SDK 内部代码）；同时，上下文里越早出现的假设越容易被一路沿用（锚定效应）。

因此在本工作流中：
1. **先喂硬件事实与边界，再动手改码**；
2. **获取到的硬件定点、命令语义与排查结论必须及时落盘到固定位置**，避免长会话压缩或新开会话后失效、重复做无用功；
3. **所有命令、DTS 与构建行为以项目源码和编译产物为准，不凭记忆猜测**；
4. **连续受阻时强制列多假设排序验证，打断单一错误路径**。

## 1. 事实与锚点落盘规范（放哪、何时读写）

在项目内为不同类型的定点设立固定落盘位置，按“先读后写、随得随记”执行：

| 信息类型 | 落盘位置 | 何时写入 / 更新 | 何时读取 |
|---|---|---|---|
| **板级硬约束与红线**<br>SoC/板型、strap 固定值、SDK 黑白名单、不可逆红线、救砖方式、三连验证规则 | `AGENTS.md`（项目根目录，模板见 [assets/AGENTS.embedded.md](assets/AGENTS.embedded.md)） | 项目初始化，或新确认一条板级硬约束/边界时 | 每次新会话自动加载 |
| **硬件拓扑与手册原文**<br>外设连接表、pinmux、时钟表、datasheet 寄存器/时序原文摘录、实测芯片 ID | `docs/hardware/`（如 `hw_connections.md`、`datasheets/`） | 拿到原理图、datasheet 原文或板端实测 ID 当轮立即写入 | 改驱动、改 DTS、查寄存器或引脚复用前先读 |
| **编译、打包与刷机命令**<br>经源码 `grep` 核对后的真实命令、隐形脚本开关（如 `generate_linux_its`）、救砖步骤 | `docs/build_and_flash.md` | 首次在源码中核对清楚并验证通过后写入 | 后续每次编译、打包、刷机前直接复用，不再重复 grep |
| **动态调试状态与已排除假设**<br>当前目标、**已验证事实（附证据）**、**已排除假设（防止重踩）**、当前候选假设与下一步 | `STATE.md`（项目根目录，模板见 [assets/STATE.template.md](assets/STATE.template.md)） | 每次完成关键验证、读回寄存器或证伪某个假设后立刻更新 | 新会话或长对话继续时**第一步先读** |
| **单次实验产物与报告**<br>测试分支的 `report.md`、patch、原始串口 log 与固件校验信息 | `reports/<分支名>/`（如 `reports/test-20261125-flash-01/report.md`） | 每次测试分支实验结束时归档（无论成败） | 回溯历史尝试、排查回归或整理合并说明时 |
| **跨项目通用坑点与私有凭据**<br>与具体板子无关的芯片/工具链共性经验、账号/密钥 | OpenViking（可选，跨项目记忆） | 沉淀通用经验或保存私有凭据时 | 跨项目检索经验或获取凭据时（不混入项目 Git 仓库） |

### 落盘与 sort-out 联动四条纪律
1. **聊出来就落盘**：对话中一旦确认了硬件事实、有效命令、寄存器读回值或证伪了某个假设，当轮立即写入对应文件，避免长对话压缩或新开会话后失效。
2. **先读定点再动手**：开始工作或新开会话时，按 `AGENTS.md` → `STATE.md` → `docs/hardware/` & `docs/build_and_flash.md` 顺序读取已有定点；已被 `STATE.md` 证伪的假设不得在无新证据的情况下重复尝试。
3. **敏感信息与大文件边界**：凭据/密钥不写入项目 Git 文件（放本地忽略的 `.env` 或 OpenViking）；大体积固件二进制建议 `.gitignore`，在 `reports/<分支名>/report.md` 中保留文件名、大小与 `crc32`。
4. **与 `sort-out` 联动（先初始化、再登记，兼容多对多）**：
   - **无配置先调 `sort-out`**：读写或初始化 `AGENTS.md`、`STATE.md`、`docs/hardware/*`、`docs/build_and_flash.md`、`reports/*` 前，先检查目标项目根目录是否存在 `sort-out.config.txt`；**若不存在，先调用一次 `sort-out` skill 初始化 `sort-out.config.txt`**，再继续复用已登记路径或落地文件。
   - **登记全部配置路径与所属 Skill**：把本 skill 用到的所有配置文件/持久化路径分别登记到 `sort-out.config.txt`，写明 `关联Skill` 为 `embedded-dev-workflow`（1 Skill → N Files）；若某文件同时被其他 skill（如 `sc-clsemi-flow`）使用（1 File ← N Skills），在 `关联Skill` 中逗号追加 `embedded-dev-workflow` 而不覆盖已有项，修改共享文件时仅增量更新；后续运行 `sort-out` 时也可适当补充完善登记说明。

## 2. 开工前：收集硬件事实

在开始调试或修改驱动前，先把以下硬件事实明确并落盘到 `AGENTS.md` 与 `docs/hardware/`：

1. **框图与器件连接表**：整理每个外设/器件到 SoC 的连接方式——接口类型（SPI / MDIO / SerDes / I2C 等）、挂载控制器、片选或设备地址、复位 GPIO 与中断 GPIO，写入 `docs/hardware/hw_connections.md`。
2. **硬件 strap 决定的不可变属性**：例如 Switch 上联模式（SGMII / HSGMII / USXGMII）、速率、PHY 地址等常由 bootstrap 电阻决定，软件既改不了也未必能读出；必须显式写入 `AGENTS.md`（「该项由硬件决定，值为 X」）。
3. **优先寻找参考固件与对照物**：老固件 ROM、厂商 EVB 镜像、同芯片其他产品的 DTS。对照已知可工作的参考做 diff，远快于从零猜测。
4. **器件关键属性**：
   - Flash：JEDEC ID、容量、页/块大小、支持的读模式；
   - PHY / Switch：芯片 ID、支持的接口模式；
   - 内存：型号、容量与频率。
5. **pinmux / GPIO 复用表**：遇到“驱动逻辑看似正常但无响应”时，先核对原理图与 SoC 引脚复用表，排除复用冲突并记入 `docs/hardware/`。
6. **时钟与参考时钟**：明确 SerDes 参考时钟（如 `125 MHz` vs `156.25 MHz`）及 MDIO/SPI 总线时钟频率。
7. **直接引用 datasheet 原文**：寄存器表、strap 表、复位与时序图直接摘录原文片段放入 `docs/hardware/datasheets/`，避免口头转述导致位宽、极性或延时出错。

## 3. 定边界与安全红线

1. **SDK 可改 / 不可改范围**：明确目录级白名单与黑名单（例如「允许改 `board/xxx/`、`dts/`，禁止改 `sdk/drivers/`」）。需要触碰黑名单文件前，必须先停下来向用户说明原因并征求确认。
2. **开发初期禁用硬件看门狗**：看门狗复位会截断串口日志并制造随机故障假象；记录禁用方法并在量产前恢复。
3. **多人 / 多 Agent 协作分工到文件**：明确各自负责的文件范围，修改他人或并行任务涉及的文件前先沟通，避免互相覆盖（如喂狗逻辑或内存配置被意外删改）。
4. **不可逆操作红线（只能提出，严禁自动执行）**：涉及 OTP、eFuse、secure boot 密钥、bootloader 分区、出厂校准分区的写入或擦除命令，只能给出方案和命令供人工审核，严禁自行执行。
5. **动 Flash 前先确认救砖路径**：确认 TFTP、USB 烧录、JTAG 或双镜像中至少一种救砖方式可用，再执行 Flash 写入操作，并将救砖步骤记入 `docs/build_and_flash.md`。

---

## 4. 开发中：以源码和实测为准

1. **命令语义先 grep 源码确认，并沉淀到 `docs/build_and_flash.md`**：严禁凭印象拼写 U-Boot 或板端专用命令。例如 `ubi write.part`（5 参数）为续写而 `ubi write`（4 参数）为先擦后写，不同 MDIO 工具可能走不同底层驱动而破坏特定器件时序；使用前先 `grep` 现有源码或脚本中的真实用法，核对通过后写入 `docs/build_and_flash.md` 供后续复用。
2. **新器件先加 debug 观测再调功能**：网口先输出 link 状态、速率、双工、MAC link、SerDes sig/sync；Flash 先输出 Manufacturer/JEDEC ID 与状态寄存器。先能“看见”，再调通功能。
3. **复位时序显式化**：对 Switch / PHY 等器件显式执行「拉低 → 按 datasheet 延时 → 释放 → 按 datasheet 延时」，不依赖上电默认状态。
4. **区分“两端匹配”与“独立自协商”链路**：明确标出哪些链路需要两端配置严格一致（如 SoC SerDes `2500Base-X` ↔ Switch EXT `HSGMII`），哪些口（如面向 PC 的 UTP 口）为独立自协商。
5. **盘点构建与打包脚本中的隐形开关**：梳理影响最终镜像内容的脚本（如 `generate_linux_its` 是否生成特定 `conf_ub_*` 或选择特定 DTB/SerDes 节点），一并记录到 `docs/build_and_flash.md`。
6. **先低速、简单模式跑通，再提速**：Flash 先单线低频再开 Quad/高频；SPI、MDIO 先降频验证。避免将信号完整性问题与驱动配置问题混在一起。
7. **寄存器写完必须读回确认**：通过 `devmem`、`mdio read` 等手段读回寄存器实际值，不把“执行了写操作”当成“配置已生效”。
8. **确认驱动真正编入并完成 probe**：核对 `.config` / `/proc/config.gz` 中的 `CONFIG_xxx`，并检查 `dmesg` 中的 `probe` 成功信息或 `deferred probe` 原因。

## 5. 排查：防锚定与证据闭环

1. **卡住协议（连续两次尝试失败时触发）**：停止沿当前猜测继续打补丁，必须列出 **≥ 3 个候选假设**，按以下结构排序后再动手验证，并同步写入 `STATE.md`：

   | 候选假设 | 支持证据 | 反对证据 | 验证方法 |
   |---|---|---|---|
   | 假设 A | ... | ... | ... |
   | 假设 B | ... | ... | ... |
   | 假设 C | ... | ... | ... |

2. **严格区分「已验证事实」与「推测」**：汇报排查进展时，显式标注哪些结论来自源码或实测日志，哪些属于尚未验证的推断；已确认的事实与已证伪的假设当轮写入 `STATE.md`。
3. **优先物理层与底层状态定位**：先观察网卡指示灯、link/speed/sig/sync 等物理层信号，快速判断卡在物理层、链路层还是协议层。
4. **一次只改一个变量**：避免同时修改 DTS、驱动和构建脚本，确保每次验证都能明确归因。
5. **获取完整原始串口日志**：要求提供从 BootROM 开始、带时间戳的完整串口日志，不依赖对报错的口头转述。
6. **构建串口 + 电源自动化闭环（条件允许时）**：使用 `pyserial` / `expect` 配合可控电源继电器，实现「刷机 → 上下电重启 → 抓取完整串口日志 → 自动判定结果」闭环，减少人工反复贴日志的误差与耗时。

---

## 6. 验证：确认板子跑的正是本次改动

1. **“实际运行的是什么”三连验证**：
   - ① 检查启动日志中的 `Model:` 字符串，确认实际加载的 DTB；
   - ② 用 `fdtdump` 检查**最终编译产物**中的 DTB 节点，而不是只看 DTS 源码；
   - ③ 用 `objdump` / `strings` 检查最终二进制文件，确认目标改动已编入。
2. **烧录校验闭环**：烧录前后核对镜像文件大小与 `crc32` 校验值，防止按旧镜像大小截断写入或写入不完整。
3. **警惕增量编译旧产物**：关键验证前执行一次 clean build，或核对目标产物的修改时间戳。
4. **记录配套组件版本**：在测试报告中写明本次测试配套的 U-Boot、kernel、DTB、rootfs 与工具链版本。

---

## 7. 分支、测试报告与模板初始化

1. **每次尝试独立测试分支**：例如 `test/<基线>-<功能>-<序号>`（如 `test/20261125-flash-01` ~ `-04`）；失败的尝试也要保留分支，确认通过后再合并主干。
2. **每个分支沉淀测试报告到 `reports/<分支名>/`**：记录基线分支/commit、patch、固件文件名 + size + `crc32`、完整串口日志与结论（失败同样记录）。
3. **提交前后 Diff 复核（防注释与文档过期）**：代码改动与相关注释、计数/总数说明、寄存器/DTS 注释或配套文档（如 `docs/hardware/`、`docs/build_and_flash.md`、`STATE.md`、`README.md`）往往不在同一位置，容易导致注释或文档过期。
   - **提交前**：先执行 `git diff`（及 `git diff --staged`），逐项确认关联注释、计数说明及相关文档是否已同步更新；
   - **提交后**：执行 `git diff HEAD~1 HEAD`（或 `git show`）对比前后两次提交再做一次复核，确认无遗漏同步或过期说明。
4. **改动归属交叉追踪**：出现构建脚本或环境配置归属争议时，使用 `git log`、文件 `mtime` 与命令历史交叉核对。
5. **项目级规则与状态文件初始化**：
   - 初始化项目规则：读取 [assets/AGENTS.embedded.md](assets/AGENTS.embedded.md) 模板，结合当前板型、SoC、串口与构建信息填空后写入项目根目录的 `AGENTS.md`。
   - 初始化状态追踪：读取 [assets/STATE.template.md](assets/STATE.template.md) 模板，写入项目根目录的 `STATE.md`，并在每次关键验证后更新。
